This issue is an internal bug report with no external linked artifact. It describes a race condition in AgentScheduler.force_cleanup() where two run-once expiration paths (a 10-minute every-minute orphan check and a 7-day general expiration) read a persisted snapshot with run_count == 0 and delete the row, but concurrent _fire() activity can increment run_count or remove the job during that interval. The issue requests either a store-side conditional delete that verifies run_count == 0 at deletion time, or shared synchronization that serializes cleanup against the first-fire transition. No external code, library, or design pattern is linked; the solution must be derived from the existing scheduler and store architecture.

## Implementation Prompt

The race condition is in packages/scheduler/scheduler.py. Both expiration paths in force_cleanup() read a persisted snapshot where run_count == 0, then delete the row and remove the in-memory job. Concurrent _fire() can increment run_count or remove the job between the snapshot read and the deletion.

Approach: implement a store-side conditional delete. Add a method to the schedule store interface named delete_if_unfired_run_once(schedule_id) -> bool that atomically deletes the persisted row only if run_count == 0 AND the schedule is a run-once schedule, returning True on success or False if the condition was not met (row already fired, already deleted, or not run-once). For the SQLite implementation, this is a single DELETE ... WHERE id = ? AND run_count = 0 AND cron_pattern = '<run-once-sentinel>' statement checking rowcount. For MongoDB, use deleteOne with the same filter and check deleted_count.

Assuming the store interface is defined as an abstract class or Protocol with SQLite and MongoDB implementations (unverified) — if wrong, the method names and location change but the pattern is identical.

In force_cleanup(), replace the unconditional delete calls in both the 10-minute orphan path and the 7-day expiration path with calls to the conditional delete. Only call self.scheduler.remove_job(schedule_id) and increment summary["expired"] if the conditional delete returns True. If it returns False, skip the job silently — _fire() owns it now.

In _fire(), no structural change is needed. The existing run_count increment and in-memory job removal already happen. The conditional delete simply loses the race when _fire() has already incremented run_count, which is the correct outcome.

Tests must deterministically exercise the interleaving for both expiration paths. Use a stub store whose conditional delete blocks on an asyncio.Event until _fire() has incremented run_count, then returns False. Verify summary["expired"] does not count the job and the in-memory job is not removed. Also add a test where _fire() has not started: conditional delete returns True, summary["expired"] increments, in-memory job is removed. Existing cleanup tests for disabled jobs, non-matching cron, and already-fired jobs must continue to pass unchanged.

The critical step is the conditional delete itself — if the WHERE clause is wrong, either fired jobs get deleted (data loss) or unfired jobs never get cleaned up (leak). Verify the filter matches exactly what the codebase uses to identify run-once schedules by reading the schedule model and the existing run-once detection logic before writing the SQL/filter.
